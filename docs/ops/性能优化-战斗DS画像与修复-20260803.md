## 2. 画像结论（定谳）

### 2.1 CPU — 战斗窗口 365s，GameThread 忙 320s ≈ 0.88 核（占全进程 93%，其余 15 线程合计 <8%）

| 排名 | 系统 | 占忙时 | 证据（窗口内累计） |
|---|---|---|---|
| 1 | 怪物 CharacterMovement | **~38%** | 2.61M 次移动组件 tick（139/帧）；`ComputeFloorDist` **独占 48.8s=15%**；GeomSweepSingle/Multiple 共 5.3M 次 91s；`ResolvePenetration` 19.8 万次 27.2s |
| 2 | Tick 调度机器 | ~14% | 11.2M 个 FTickFunctionTask（598 个/帧）；QueueTicks 16.3s + ResetTickGroup 10.5s + ProcessUntilTasksComplete 11.9s 均为纯调度 |
| 3 | 网络复制 | ~11% | ServerReplicateActors 33.9s；1.64M 次 actor 复制、5.87M 次属性比较——仅 1 个连接 |
| 4 | Chaos 物理 | ~9% | 主要是 150 角色的 kinematic 更新（AdvanceOneTimeStep 14.4s 等） |
| 5 | RHI/渲染残迹 | ~1.9%（修正值） | 调用树单链 `Render_EndFrame→RHICmdList_Submit→RHITaskPipe→GPUProfiler::ProcessEvents`，不重叠合计 ~6s；早期 3-4% 是嵌套重复相加的高估 |
| 6 | GAS | ~2% | 84.4 万次 ASC tick 6.1s（NPC ASC 复制模式已是 Minimal，无需改） |

### 2.2 内存 — LLM 标签归属

- 空载 361MB，8 分钟曲线纹丝不动，**无泄漏**。
- 战斗 RSS 1.16~1.31GiB（真实堆 FMalloc 785MB；LLM 采集自身开销 ~146MB 已含）。
- 增量几乎全部是 **Physics 家族 ~558MB**：ChaosAcceleration 164 + ChaosGeometry 122 + ChaosUpdate 68 + ChaosBody 51 + ChaosActor 45 + StaticParticles 38 + Trimesh 20；其余系统全部个位数 MB。战斗图加载时一次性跳上去，之后平稳。
- 14Gi limit 对实际 1.3GiB 严重超配，可灰度降 4Gi（K8s 配置，另行拍板）。

### 2.3 停摆炸弹 — NoFOW（空载会话铁证）

- `/Game/LayeredFOW_Edit/MiniMapSystem/NoFow/BP_NoFOW_Minimap` 在 DS 上每帧 `GetPlayerPawn→GetPlayerCameraManager→MinimapWidget` 三连 Accessed None + 整份脚本栈转储；空载忙时占 21%、日志占 14%（均值 354 条/s、峰值 851 条/s）。
- 抓到一次 **2.65 秒整世界停摆**，调用链逐帧可循：`TG_PrePhysics → FTickFunctionTask → BP_NoFOW_Minimap.ReceiveTick → ExecuteUbergraph → STAT_FMsgLogf 2.6503s`（日志写线程反压，同 hub DS 卡死同源）。
- 战斗窗口它本体仅 0.9s——罪在停摆风险与日志，不在均值。

### 2.4 根因链 — 怪物卡岩石（三个症状一个病）

1. **navmesh 与物理世界不一致**：PCG 摆的岩石 ISM（`ISM_SM_Rock_Flake/Cliff_Rock/Rock_Boulder`、`BPP_Rock_Arctic_PageRock`）有阻挡碰撞；组件 `bCanEverAffectNavigation` 为默认 true（uasset 无覆盖串），但**烘焙 navmesh 未刻入岩石**（最可能：摆完没重烘）→ 选路穿岩石 → 水平 sweep 被真实碰撞挡住 → 永远到不了路点，每帧穿透解算。
2. **出生点静默回退**：`ResolveSpawnLocation` 在 `GetRandomReachablePointInRadius` 失败（WP 服务器流送下导航分块未就绪）时回退裸 SpawnCenter 硬塞，`AdjustIfPossibleButAlwaysSpawn` 对 trimesh 解不开 → 怪永久嵌入。
3. **碰撞复杂度**：ScifiArctic 63 个网格 `CTF_UseComplexAsSimple`（含 SM_Cliff_Rock 全系/Medium_Rock/Rock_Wall/Pillar/Plate/Mesa/Cave_Hexa/Volcanic 等）——角色扫掠直接怼原始三角网格，`ComputeFloorDist` 的 15% 与 Physics 内存 558MB 同源。
- 引擎事实（5.8 源码核实）：NavWalking 治「扫地贵」不治「卡岩石」（`PhysNavWalking` 仍走 `SafeMoveUpdatedComponent(bSweepWhileNavWalking)` 水平扫掠）；`SetGroundMovementMode(MOVE_NavWalking)` 保证击飞进 Falling 落地后自动回落；投影不到 nav 时 StartFalling/退 Walking 有兜底。**顺序必须是先修数据再切模式**。

### Q1：这些修复所有地图都能用吗？以后新加的地图也能吗？

分三类，覆盖面完全不同，**不要笼统说「全都自动生效」**：

| 修复 | 作用域 | 新地图 |
|---|---|---|
| NoFOW 蓝图守卫（§3.2） | 改的是**类**，任何图里放这两个 BP 都生效 | ✅ 自动 |
| NPC 专服 cvar（§3.1 #2#3） | 挂在 `AMyNpcCharacter`，全部怪物子类继承 | ✅ 自动 |
| 刷怪导航兜底（§3.1 #1） | 走公共刷怪链，所有关卡共用 | ✅ 自动 |
| `WITH_RHI_BREADCRUMBS=0`（§3.1 #4） | 编译期全进程 | ✅ 自动 |
| **navmesh 刻岩石、碰撞简化** | **逐图/逐资产的数据工作** | ❌ **需逐图做** |

**因此新增战斗地图必须进检查表**：①摆完 PCG/岩石后重烘 navmesh 并目检有洞；②新引入的地形/岩石网格若用 `UseComplexAsSimple` 且是障碍类，配简单碰撞；③新怪物蓝图勾掉 Mesh 的 `bEnablePhysicsOnDedicatedServer`（见 §4.1 第 3 条，模板勾上可让后续新怪默认安全）。建议把这三条写进关卡/怪物的接入规范。

### Q2：能不能"直接只留怪物的寻路世界（navmesh）"？

**可以，引擎这条路是通的，但顺序必须是"先把 navmesh 做对，再切 NavWalking"**——这两件事是前提关系，不是并列关系。UE 5.8 源码三条关键事实：

1. **水平碰撞还在**：`PhysNavWalking` 的位移仍走 `SafeMoveUpdatedComponent(..., bSweepWhileNavWalking, ...)`（默认开 sweep）。NavWalking 省掉的只是**每帧向下找地面**的 `ComputeFloorDist`——脚下高度改从 navmesh 投影（`FindNavFloor`）取。**所以怪不会穿墙穿岩石**。
2. **击飞/坠落能自动回来**：`SetGroundMovementMode(MOVE_NavWalking)` 记住"落地后回什么模式"，被击飞进 Falling、落地后自动回 NavWalking，不会卡在错误模式。项目有击飞死亡（`BeHitAir`），这条是必要保障，代码里已按此写。
3. **走出 navmesh 有兜底**：投影不到 nav 点时进 `StartFalling` 或退回 `MOVE_Walking`，不是卡死。
4. 死亡 ragdoll 不受影响（走 mesh 物理，不经 CMC）。

**关键推论**：卡岩石的链条是「navmesh 没刻岩石 → 选路穿岩石 → 水平 sweep 被真实碰撞挡住 → 永远到不了路点」。切 NavWalking 后水平 sweep 仍在（事实 1），**怪还是会卡，只是每帧便宜一点——止痛不除病**。故：
- 第一步（必做，纯数据、零行为风险）：把 PCG 岩石刻进 navmesh。做对了怪就绕着走，病理性的那部分（卡住反复扫地）直接消失。
- 第二步（可选，行为改变）：再切 NavWalking 省掉"正常走路"的扫地成本。**用第一步之后的画像数据决定**——38% 里多少是病、多少是正常走路的钱，现在分不出来。
- 这就是 `NpcServerNavWalkingMode` **默认取 0** 的原因。

落地纪律（做第二步时）：只动怪不动玩家；按 §17 走表（`CfgRole` 或刷怪点加"移动模式"列），不写 `if (RoleId == N)`；上线前按 §8 压测口径拿对比数据，`CharPhysNavWalking` 有独立 stat，与现在的 `Char PhysWalking` 直接可比。

### Q3：能不能"需要的时候场景物理才开始走"——人和怪不碰的时候就别跑 PCG/岩石的物理？

**结论：不需要做，因为省不到东西，而且自建会打穿正确性。**

- **静态碰撞体没有每帧成本**。岩石是静态刚体，不参与求解器积分；它们只在**别人查询时**被访问（角色扫掠、射线）。画像里 Chaos 那 9% 是 150 个角色自身的 kinematic 更新，不是岩石在跑。所以"没人靠近就别跑岩石物理"这件事，**本来就没在跑**。
- **真正的成本在"查询时的几何复杂度"**，不在"物理开没开"——所以正解是把 trimesh 换凸包（§4.1 第 2 条），一次改动永久降量级。
- **该有的按需已经有了**：WP 服务器流送（`wp.Runtime.EnableServerStreaming=1`）保证未加载 cell 的碰撞根本不存在；NavWalking 档位 2 让移动完全不查几何。语义已被覆盖。
- **自建"延迟建物理"会 fail-open**：技能射线、落地检测、视线判定随时可能查询任意位置的几何，若那一刻物理体还没建，会静默返回"没有东西"——这是把确定性错误变成随机错误，违反第 3 条（宁可 fail-closed 拒绝也不写不自洽的数据）。

### Q4：技能要在运行时改变"可走/不可走"区域（含时效后恢复），怎么做？

引擎有正路，且**不需要跳到全量 Dynamic**——`NavigationData.h:522` 的三档正好有个为此设计的中间档：

```
Static               // 纯烘焙，运行时不可变（当前档位）
DynamicModifiersOnly // 几何烘死，只允许运行时改"区域标记"  ← 技能玩法要的就是它
Dynamic              // 几何+标记全动态（DS 上的性能炸弹，不需要）
```

三种场景逐一对应：

- **可走 → 变不可走**：技能 Actor 挂 `UNavModifierComponent`（有 `SetAreaClass` 运行时 API），区域标成 `NavArea_Obstacle`（绕行）或 `NavArea_Null`（从图里抠掉）。组件注册时只重建被碰到的那几个 tile，**技能 Actor 销毁时自动注销、tile 恢复烘焙原状**——时效性天然免费。
- **不可走 → 变可走**：分两种。①**有面、被标记不可走**（平地禁区/毒圈）：运行时换 area 标记即可翻转。**设计纪律：想运行时翻转的禁区，烘焙时要用 modifier 标记，不要把几何本身抠掉**。②**根本没面**（悬崖/深渊/水面，烘焙时就没生成多边形）：modifier 变不出面来，正路是 `UNavLinkCustomComponent`（有 `SetEnabled(bool)` 运行时开关），技能激活时开、失效时关，寻路会纳入/剔除；怎么"过去"由 `OnLinkMoveStarted` 回调自定义。
- **时效结束恢复**：如上，modifier 随 Actor 销毁自动还原，link `SetEnabled(false)`，都是引擎内建，不用自己写恢复逻辑。

三条必须守住的纪律：
1. **nav 和碰撞必须同步双改**。只放碰撞不挂 modifier → 怪照样选路进去、撞上、卡死（PCG 岩石病在技能系统里重演）；只改 nav 不放碰撞 → 玩家能进怪却绕开，表现也错。建议将来把"modifier + 碰撞"封成一个组件对，杜绝只改一半。
2. **站在里面的怪要善后**。翻成 `NavArea_Null` 时面从图里消失，NavWalking 的怪若正站在里面，`FindNavFloor` 失败会触发 `StartFalling`/退 Walking。所以"怪可能站在里面"的区域优先用 `NavArea_Obstacle`（面还在、代价高、寻路绕开），`Null` 留给物理上也进不去的实心技能。
3. **瞬时技能别挂 modifier**。tile 重建是事件驱动、按技能数量有界的——前提是只有持续型区域技能才挂。弹道/瞬发挂上去就是 tile 重建风暴，违反第 5 条。

**对当前计划的影响：零**。`DynamicModifiersOnly` 空闲时无每帧开销（不需要几何入 octree，`NavigationSystem.h:1446`），成本是 tile 压缩缓存随图带（包体/内存略增，量级需实测）。按第 6 条，**这类技能真立项了再切枚举**，现在不用动；切档只是 RecastNavMesh 上改一个设置加重烘，**现在刻岩石的工作不会白做，两者完全兼容**；NavWalking 也不受影响（modifier/link 改的是 navmesh 本身，怪自动跟着新图走）。

### Q5：为什么不给性能监控 / AIC / ASC tick 也降频？

见 §3.3。核心是三条：`Tick_PerformanceMonitoring` 在 Development 无任何开关且 Shipping 自动消失（战斗仅 0.4%，动引擎不划算）；AIC tick 驱动路径跟随，降频伤转向品质，收益（~1%）不抵风险；NPC ASC 复制模式**本来就已经是 `Minimal`**（`MyNpcCharacter.cpp:15`），无需改。

### 6.1 官方 UE MCP 做蓝图图手术

编辑器需在跑且 MCP 服务已起（控制台 `ModelContextProtocol.StartServer`，默认 `127.0.0.1:8000/mcp`）。走 JSON-RPC：`initialize` 取 `Mcp-Session-Id` → 后续每次带上；因 `bEnableToolSearch=true`，真实工具经 `call_tool{toolset_name, tool_name, arguments}` 派发。本次用到的完整链路：

```
list_graphs(blueprint)                     → 拿 EventGraph 的 refPath
find_nodes(graph, title[, entry_points_only]) → 定位事件节点（title 必填；空串+entry_points_only 可列全部入口）
get_node_infos(nodes)                      → 拿每个 pin 的 direction/index_id 与现有连接（接线全靠这个）
find_node_types(graph, type_id_filter, context_pins) → 查 type_id
create_node(graph, type_id, pos)           → 建节点
break_pins / connect_pins(output_pin, input_pin)     → 改接线，pin 用 {direction,index_id,node:{refPath}}
compile_blueprint(blueprint)
AssetTools.save_assets(asset_paths)        → 必须显式存盘，否则只在内存
read_graph_dsl(graph)                      → S 表达式回读验证（本次确认守卫结构就靠它）
```

本次用到的 type_id：`Networking|IsDedicatedServer`、`Utilities|FlowControl|Branch`、`Actor|DestroyActor`。

已知坑：①多条命令连发偶发挂起触发 2 分钟超时，**重发剩余命令即可续**（前面的已生效，别整批重来）；②`find_nodes`/`find_node_types` 的必填参数名是 `title`/`type_id_filter`，传错会报出完整 schema（可用作探测手段）；③编辑器崩溃/重启后 session id 失效，需重新 `initialize`。
