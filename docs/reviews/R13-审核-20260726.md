## 2. 确定性交错验证

### 2.1 Login A→B→C 三方交错

验证目标：B 的 Redis 写成功但从未交付给客户端，C 失败后补偿不恢复未交付的 B。

```text
初始：A/gen1 已交付，Redis/MySQL 均为 A。
Login B：写入 B/gen2 成功，响应丢失。
Login C：写入 C/gen3，后续失败。
R13 补偿：MySQL 对 C 条件墓碑(jti=C,gen=3)；Redis FenceFailedSet(gen<=3)清能力+推水位。
Login B 迟到补偿：看到 gen3 > gen2，no-op。
```

结论：不再恢复 B。下次 Login 以 gen4 自愈。常驻回归 `TestRedisSessionFailedABCInterleavingNeverRestoresUndeliveredB` 覆盖。

### 2.2 COMMIT 模糊 + gen 复用

验证目标：B 的 MySQL COMMIT 结果不确定且未落地，C 复用同 generation，B 的迟到消歧不得清掉 C。

```text
B COMMIT 模糊 → 读回 not-found → generation 未被持久占用
C 以同 gen 成功 → MySQL/Redis 均为 C
B 迟到消歧：MySQL TombstoneFailedSessionJTI(jti=B,gen=N) → 条件 UPDATE 0 行(当前 jti≠B) → fenced=false → 禁止 fence Redis
```

结论：未证实 generation 占用不允许清 Redis。常驻回归覆盖。

### 2.3 writerlease 截止过期后迟到 TTL proof

验证目标：proof 调用期间本地 deadline 过期，返回的 TTL 不得复活同 token。

```text
holdState.selfFenced 在 deadline 过期时设为 true（单调终态）
applyTTLProof 在 store 后 double-check selfFenced → 发现已 true → 不恢复
```

结论：proof 结果到达时若已自 fencing，永不复活。

### 2.4 assignment tombstone ABA

验证目标：同一 writer term 两次删除同一玩家，A 的迟到补偿不得把 B 的更新恢复成旧归属。

```text
Delete(A): 写 tombstone{assignment_id=uuid-A, writer_token=7}
正常归属恢复或新写入覆盖 tombstone
Delete(B): 写 tombstone{assignment_id=uuid-B, writer_token=7}
A 迟到补偿: proto.Equal(cur, intended-A) → uuid-A ≠ uuid-B → false → 不恢复
```

结论：操作身份区分了同 token 的不同删除。

### 2.5 UE 门闩交错

验证目标：旧 SelectRole(A) 回调迟到不阻塞新 ROLE_REQUIRED 后的确认。

```text
SelectRole(A) 发出 → bSelectRoleInFlight=true
权威换代 → A 失效 → ROLE_REQUIRED → HandleAuthoritativeRoleRequired → bSelectRoleInFlight=false
A 回调迟到 → IsCallbackCurrent(A)==false → return（不改门闩）
玩家再次确认 → bSelectRoleInFlight==false → 正常发出新 RPC
```

结论：修复完整，不需要额外机制。

## 3. 审核发现

### P1-1｜writerlease `holdUntilTermEnds` 单次 proof 失败过激自 fencing（行为回归风险）

- **位置**：`pkg/dsauthfence/writerlease/writerlease.go` `holdUntilTermEnds` 内 proof 失败分支
- **现象**：ticker 周期调 `term.RemainingTTL` 失败一次即调 `selfFenced.Store(true)` + Resign，任期永久死亡。etcd 瞬时超时/网络抖动即可触发。
- **基线行为**：基线用 ticker 无服务端确认续期，虽然不安全（INC-001 直接根因），但不会因单次抖动终结任期。
- **R13 行为**：单次 proof 失败 → selfFenced 永久终态 → 该 token 再也无法续活 → 重选举 → 推扫 → 所有在途写补偿。频繁 etcd 网络抖动会造成反复重选举 churn，基线不存在此问题。
- **建议**：proof 失败时只"不续期"（让现有 deadline 自然过期），不立即 selfFence。连续 N 次失败（如 3 次）且 deadline 确实过期后再永久自 fencing。这保留了"失联自动止损"的安全性，同时容忍单次抖动。
- **定性**：P1。不是代码错误，是安全与稳定性的权衡点；当前选择偏向安全但引入了基线不存在的 churn 模式。
- **验证门**：需要真实 etcd 多副本 + 注入瞬时超时，观察重选举频率。

### P1-2｜`FenceFailedSet` 范围条件确定性踢在线玩家 A（有意取舍，需运维文档）

- **位置**：`services/account/login/internal/data/account.go` `fenceFailedSetScript` Lua
- **现象**：A→B 两方场景（最常见）：A 已交付且在线，B 的 Redis Set 失败。`FenceFailedSet(failedGen=genB)` 检查 `cur.gen <= failedGen`。因 genA < genB，A 的能力被清除——在线玩家 A 被踢。
- **R12 行为**：`DeleteIfJTI(B)` 只精确删 B，A 不受影响。
- **R13 行为**：安全优先——无法证明 Redis 当前值是已交付的 A 还是未交付的 B（三方交错时可能是 B），宁可踢 A 也不留未交付 B。客户端收到 `ErrUnavailable` 后重试以 gen+1 自愈。
- **定性**：P1 行为回归。这是 INC-002 §5 明确记录的有意取舍，不是 bug。但运维和 SRE 需要知道："B 的 Redis 写失败"会导致"A 被踢"，且这是设计预期而非异常。需要在 ops/运维文档或告警 runbook 里说明此行为。
- **验证门**：运维文档补充此行为说明。

- **位置**：`services/account/login/internal/biz/login.go` `resolveAmbiguousSessionGeneration` 内

## 8. 架构级单写者闭环分析：为什么 Redis HA 层修不了

### 8.1 fencing 的数学前提

本轮全部 fencing 的正确性归结为一条不变量：**水位单调不回退**——`writer_token`、`generation`、墓碑一旦被 Redis ACK，永不消失、永不变小。

证明链：

```text
etcd token 严格递增（线性一致，这半边没问题）
   ↓
Redis 水位只进不退          ← 全部正确性押在这一条
   ↓
迟到旧写者必然读到 ≥ 自己的水位 → 零写入
```

Redis Sentinel/Cluster 是异步复制：主库 ACK 一笔写 → 还没复制出去就挂了 → 副本晋升 → **这笔已确认的写凭空消失**。水位回退了。

后果：被 fence 出局的旧写者重读，看到回退后的旧水位 → 比较通过 → 合法写入 → **借尸还魂**，且每一步在它自己看来完全合法。应用层无法检测：新主库没有"我丢过写"的标记，回退后的状态和从未发生过那笔写的状态在字节上不可区分。

### 8.2 三种"看起来能修"的方案为什么都是假的

| 方案 | 为什么不行 |
|---|---|
| **写后回读确认** | 回读发生在主切之前，确认的是"旧主库有这笔写"，证明不了"晋升的副本也有" |
| **`WAIT N`** | 只保证 N 个副本**收到**，不保证故障切换**选中**的恰好是收到的那个；分区期间旧主还能继续收写。成功 ≠ 写在切换后存活 |
| **`min-replicas-to-write`** | 只是主库在副本不足时拒写的门槛，复制仍是异步的；`min-replicas-max-lag` 窗口内旧主照常 ACK。降概率 ≠ 给证明 |

三者共同点：把"大概率不丢"包装成"不丢"。验收底线第 3 条要求完整性证明，概率性缓解写成关闭就是掩盖。INC-001 HWF-7 明文禁止。

### 8.3 为什么不能把水位挪到 etcd/MySQL

当前设计的核心价值是**比较与写入在同一原子域**——`guardWriterFence` 的水位比较、业务写、水位推进落在同一个 Redis `WATCH/MULTI/EXEC` 里，同 slot，没有 check-then-act 窗口。

把水位搬去 etcd/MySQL，业务数据（assignment、席位、容量账本）还在 Redis：

```text
① 查 etcd 水位（通过）→ ② 写 Redis 业务数据
        ↑______这中间失租/被继任______↑
```

跨存储先查后写——正是 §9.22 点名禁止的 TOCTOU，也正是当前设计花力气消掉的东西。

**fencing 的比较点必须和被保护的写在同一个事务域里**。所以要么水位跟着数据走（现状，被 Redis 复制模型拖累），要么数据跟着水位走（真解）。

### 8.4 真正的修法为什么是另一个批次

唯一正解是后者：把"归属"这个状态本体搬进线性一致事务域——§9.22 Owner Authority：`owner_epoch`、lease 截止、`admit_not_before`、`PENDING→ADMITTED` 在同一个线性一致存储（TiDB）里完成 CAS，Redis 里的 assignment 降级为非权威投影。

这不是 hub_allocator 的一个 patch，因为消费方是全链。INC-20260722-002 §10.1 论证了五条确定性阻断：

1. Login 错误折叠 `role_id=0`（无法区分 ROLE_UNKNOWN 与未选角）
2. 票据不带 `owner_epoch`（DS 无法校验）
3. Battle `Begin` 弱依赖（失败照常交付 allocation）
4. 取消链缺 `Release`（无法按 exact 四元组精确释放）
5. 一个 match 级 epoch 不能替代每玩家权威代次

半开比不开更危险——会造出两套权威。最小不可拆分批次：Login + Hub + Battle + matchmaker + JWT/proto + UE 入场门 + coordinated rollout。

| 态 | 保护 |

| 正常态（Redis 不主切） | 进程内 fencing 正确，确定性交错测试覆盖 |
| 主切窗口 | 损害被 Admission 会话复核 fail-closed + assignment 非准入最终权威 + TTL 兜底蒸发限制成有界 |
| 终态 | §9.22 Owner Authority，设计定稿，待全链接线 |

这是验收推论要求的形态：**该修的层修到位，修不到的层不装修好**。
