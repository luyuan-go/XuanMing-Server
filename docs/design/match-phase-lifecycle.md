# 待做:对局三段式生命周期(准备阶段 / 战斗阶段 / 结算阶段)

> 状态:**待做**——需求已提出,**尚未设计、尚未拍板、零代码**。本文件只登记需求、核对现状、
> 列出必须先拍板的问题,**不预设方案**。
> 提出:2026-08-12,用户口述——「每个 PvP / PvE 都应该有三段:准备阶段、战斗阶段、
> 结算阶段(阶段完成退出场景)」。
> 适用范围:**PvP 与 PvE 一视同仁**(撮合进本与直接进本两种入口都要有这三段)。
> 关联:入口分离见 [`decision-dungeon-entry-modes.md`](decision-dungeon-entry-modes.md);
> 战斗 DS 生命周期见 [`ds-arch.md`](ds-arch.md) §6;
> 断线重连与终局投递见 [`battle-reconnect.md`](battle-reconnect.md);
> 关卡表分层见 [`decision-dungeon-scene-table-layering.md`](decision-dungeon-scene-table-layering.md)。

## 1. 需求

一局对局(PvP / PvE 都一样)在时间轴上切成三段,阶段之间有明确边界:

| 阶段 | 语义 | 结束条件 |
|---|---|---|
| **准备阶段** | 玩家陆续进场、加载 / 切场景,对局尚未开打 | 见 §1.1(已澄清) |
| **战斗阶段** | 真正的玩法进行中 | 分出胜负 / 到达对局时限(`battle_duration_seconds`,已实现) |
| **结算阶段** | 胜负已定,展示结果 | **阶段完成即退出场景**(回 Hub);内容待拍板,见 §3.3 |

### 1.1 准备阶段的目的已澄清(2026-08-12 用户补充)

> 原话:「准备阶段就是为了给卡顿的玩家切到另外一个场景准备充足的时间,一般是配置吧,
> 每个场景不一样的准备时间。」

据此**定死三件事**,不再作为待拍板项:

1. **准备阶段只解决"进场对齐",不承载玩法。** 它的唯一目的是给加载慢 / 机器卡的玩家把
   场景切完;**不做** ban-pick、选人、买装、开局演出。若将来要加这些,那是**另一个需求**,
   不得借本阶段夹带(§15.3 拒绝预设性复杂化)。
2. **时长配在关卡表,每张图一列,一图一值。** 与 `battle_duration_seconds` 并列
   (`proto/pandora/config/v1/level.proto` 的 `LevelRow`),不是全局常量——大图加载慢、
   小图快,本来就该不一样。落地细节见 §4。
3. **`0` = 不配 = 没有准备阶段(立即开打)。** 这是关卡表既有惯例:新列的 `0` 一律解释为
   "未配置 → 与本列上线前逐字节等价",保证滚动混版下新旧表都安全
   (`battle_duration_seconds` / `min_team_size` / `side_count` 全按此写)。
   **不要**把 `0` 解释成"无限等待"——那会造出一个没有出口的等待态,直接违反 §9.19 / §9.20。

### 1.2 一个必须先看的设计问题:固定时长 ≠ "等到人都好了"

需求说的是「给卡顿玩家**充足**时间」。但**纯固定时长**并不保证这件事,它只是把
「先到的人已经在打」换成「大概率够用」,并且两个方向都会翻车:

- **配短了** → 目的没达成:慢机器还没进来,快的人已经开打(与现状同病)。
- **配长了** → 每局都吃满:哪怕全员 3 秒就绪,所有人也得干等满配置值。而"最慢的那台机器"
  是长尾分布,想覆盖它就必须按最坏值配 → **常态被最坏值绑架**。

**建议(推荐,与"配置驱动、每图不同"完全不冲突)**:准备阶段结束条件取
**`全员就绪` 与 `到达配置上限` 的先到者**。于是:

- 表里那个数从「固定等待时长」变成「**最长等待时长**」——语义更准,配的时候也更好推导
  (按这张图的最坏加载耗时配,而不是猜一个折中值);
- 快的时候不浪费(全员就绪立刻开打),慢的时候有界(到点强开,不会无限等);
- 天然满足 §9.19 / §9.20「等待必须有界、到期必须自动继续」——**到期动作是"强开"而不是
  "假设都好了再等等"**,属 §16.10 判别表里的"兜底"而非"掩盖"。

若最终仍拍板走**纯固定时长**(不看就绪状态),那是可接受的简化,但必须在本文件写明
"已知快的人会干等满",别让它以 bug 的形式被重新发现。

## 2. 现状核对(2026-08-12 实查,不是推测)

**结论:三段里只有"战斗阶段"存在,而且只以"时限"这一个维度存在;另外两段完全没有。**

- **准备阶段:不存在。** 玩家 travel 完成、被 Admission 接纳后即可行动,没有任何"等待开打"的
  闸门。对局时限的**武装点是"首个玩家进入"**
  (`Pandora-Client-SVN`:`PandoraBattleGameMode.cpp` `TryArmBattleTimeLimit`),
  也就是说**先到的人已经在打,后到的人还在跑图**——这正是准备阶段要解决的问题之一。
- **战斗阶段:部分存在。** 时长读关卡表 `battle_duration_seconds`
  (`configtable/dist/level.json`,当前 1200 / 1800,`0` = 不限时),剩余秒数按**整秒**经
  `AMyGameState::BattleRemainingSeconds` 复制给客户端;到点走 `HandleBattleTimeLimitReached`
  → `EvaluateTerminalNow` 结算。**但对局本身没有"阶段"这个状态**,只有一个倒计时数字。
- **结算阶段:不存在(玩家视角)。** 服务端侧有一条终局投递状态机
  (终局快照冻结 → `ReportResult` → receipt → terminal ack,见 `PandoraBattleGameMode.h`),
  但那是**后端可靠投递机制**,不是玩家能看见的一段时间窗;没有战报 / 掉落 / MVP 展示窗口,
  也没有"结算完成"这个可被观察的事件。
- **退出场景:有链路,但不是"阶段结束"驱动的。** Battle → Hub 走 `ds-arch.md` §6.2 的
  `BattleEnded{result, hub_ds_addr, hub_ticket}` + 客户端自行发起回 Hub;
  实测 PvE 退出耗时的大头是后端再入屏障等待(`pkg/placement.DSFenceReentryBarrier` = 27s,
  login 侧表现为 `ADMIT_BARRIER`;BATTLE→HUB 这段刻意保留)。
  三段式落地后,"退出场景"必须挂到**结算阶段结束**这个边界上,而不是各自触发。

### 2.1 PVE 结算触发条件(2026-08-12 实查;**与"所有怪物死亡即结算"的说法不符**)

用户提出「每个 PvE 目前结算是所有怪物死亡结算,也就是可能会提前结算」。逐路径查证后:

**"提前结算"的担心成立,但根因不是怪物。代码里根本没有"怪物清空 → 结算"这条路径。**

- **终局触发只有三个**(`PandoraBattleSettlementRule.h` 的 `EPandoraBattleTerminalTrigger`):
  `PlayerDied`(玩家死亡)、`PlayerExtracted`(撤离成功)、`TimeLimitReached`(对局时限耗尽)。
  枚举注释明确写死「终局裁决只有 `EvaluateTerminal` 一个权威入口,新增触发原因一律加本枚举值,
  **不得**另开并列钩子」。**没有怪物相关的触发值。**
- **PVE 规则是撤离制**(`UPandoraPveSettlementRule::EvaluateTerminal`):
  **整队全部进入终态(死亡或撤离)才结算**;有任一人撤离成功 → 通关(0),全灭 → 未通关(1)。
- **怪物死亡回调不结算**(`PandoraBattleGameMode.cpp` `HandleMonsterEntityDied`):
  只做两件事——按 `CfgDrop` 产掉落、上报击杀经验事实(`ReportMonsterKillCredits`)。
  全文件 `RequestFinishBattle` 的调用点只有死亡 / 撤离 / 超时 / 失败重投四处。
- 结算规则基类虽是 `Blueprintable / EditInlineNew`(蓝图可换实例),但 `Pandora/Content` 下
  **未扫到任何引用该类的资产**,即当前没有蓝图子类改写判据。

**那"可能提前结算"从哪来的?**——来自撤离制判据本身,不是怪物:

| 场景 | 现在会发生什么 |
|---|---|
| **单人 PVE** | roster 只有 1 人 → "整队全终态" = **这一个人死了就立刻失败结算**,没有任何缓冲 |
| **多人 PVE** | 最后一个活人一撤离,**局立刻结束**——还没撤的人若已死,直接被判通关收局 |
| **打完怪之后** | 什么都不发生;局**不会**因为怪清空而结束,得靠撤离 / 全灭 / 超时 |

所以真正该记的缺口是:**"目标达成"与"对局结束"目前是同一件事**——没有任何窗口给玩家
捡东西、看战报、决定撤不撤。这恰恰是三段式里"结算阶段"要解决的问题(§3.3)。

> ⚠️ 若线上实测确实看到"怪一清空就结算",那说明存在本次未覆盖的路径(如蓝图规则实例、
> 或某张图挂了别的 `GameModeClass`),**请给出具体 map_id 与日志**再查;
> 按当前 C++ 事实不成立,不要把它当现状写进设计。

### 3.2 准备阶段

5. ✅ **准备阶段做什么** = 只做进场对齐,不承载玩法(§1.1①,已定)。
6. **结束条件取哪种**:`全员就绪 or 到上限`(推荐,§1.2)还是**纯固定时长**?

7. **"就绪"的判据是什么**(选了推荐方案才需要):必须复用既有信号,**不要新造客户端自报字段**

8. **与撮合确认(confirm)的关系**:PvP 撮合已有"全员确认"环节
   (见 `decision-dungeon-entry-modes.md`),准备阶段**不能变成第二套确认**——

9. **单人 walk-in PvE 是否跳过**:直进副本可能只有 1 人,固定等待纯属浪费。
   ——注意:选了 §1.2 推荐方案,这个问题**自动消失**(1 人就绪即开),这也是推荐它的理由之一。
10. **时限武装点怎么改**:三段式后,战斗时限应从**准备阶段结束**起算,而不是现在的
    "首个玩家进入"(`TryArmBattleTimeLimit`)。这是对**已上线行为**的语义变更,要一起改、
    一起验。
11. **准备阶段的计时起点**:同样是"首个玩家进入"?若从 DS 进程起算,大图的 DS 自身加载
    (现有注释实测"数十秒,大图更久")会把准备预算吃光——这正是当年时限选"首个玩家进入"的原因,
    别推翻它。

### 3.3 结算阶段(用户尚未细化,整段待拍)

12. **结算阶段展示什么**:战报 / 掉落 / 经验 / 段位变化 / MVP?——数据来源分散在

13. **结算阶段与终局投递的关系**:玩家可见的"结算中"窗口,与服务端 `ReportResult` → receipt →

    若不绑定,玩家可能在数据落库前就退出。**这是本项最大的正确性风险,必须显式选择。**
14. **能不能提前退**:结算阶段允许玩家点"跳过"直接回 Hub 吗?跳过后掉落 / 段位是否照发?
15. **退出场景由谁发起**:结算阶段到点后 DS 踢人,还是客户端自己走?

### 3.4 横切

18. **观察性**:阶段切换要打点(排障时"卡在准备阶段"必须能查:等谁、等了多久、为什么开)。

## 4. 准备阶段的落地约束(已查清的既有事实,实现时照抄别重查)

**新增关卡表列的机械路径**(与 `battle_duration_seconds` 完全同款):

1. `proto/pandora/config/v1/level.proto` 的 `LevelRow` 加字段——**下一个可用编号是 18**
   (17 是 `rating_pool`),写法 `uint32 prepare_duration_seconds = 18 [(excel_col) = "准备时长",
   (excel_default) = "0"];`(列名最终以策划表头为准)。
2. **xlsx 表头必须同步加列**:源表在**客户端仓** `Table/关卡/g_关卡.xlsx`
   (`LevelTableData` 的 `excel_file = "关卡/g_关卡.xlsx"`)。
   ⚠️ **登记了 proto 却没加表头 → 生成器整表拒绝**(不是 bug,是设计:未登记 / 缺列都算非法表)。
3. 加载期校验落 `pkg/configtable/level.go` 的 `validateLevelRow`(如"准备时长不得超过上限")。
4. 走 §9.15 配置表热更流水线;关卡表是**跨仓共享事实**,改表必须双仓同步发布
   (历史事故:松林镇 4002 镜像关卡表漂移)。

**配这个数时可用的既有时间预算**(别凭空拍):

| 常量 | 值 | 出处 / 含义 |
|---|---|---|
| `TravelAdmissionWatchdogSeconds` | 45s | 客户端 Travel→Admission 等待上界(`UMyDsRecoveryCoordinator` watchdog)。**超过它客户端已经在重查权威重试了**,准备时长配得比它还大没有意义 |
| `HubAdmissionTotalBudgetSeconds` | 25s(= 45 − 15 − 5,推导值) | Hub 准入链总预算 |
| DS 进程起 → 玩家 travel 完成 | 数十秒,大图更久 | `TryArmBattleTimeLimit` 注释实测口径;**这正是准备阶段要覆盖的那段** |

**不得触碰的既有约定**:

- `min_team_size`(队伍人数下限)**只在进场那一刻判定**,不是局内持续不变量。准备阶段结束时
  人数不足**不得**据此踢人或强制收局(proto 注释已写死,§9.19 / §9.20)。
- 准备阶段的等待必须有界且到期自动继续(强开),不得出现"等一个可能永不到达的回调"
  (§16.10 判别表:到期"重查权威 / 强开"是兜底,到期"假设成功"是掩盖)。

## 7. 建议方案:阶段不是状态,是从"时刻 + 判据"派生的投影

> 触发:用户 2026-08-12「你觉得最标准做法是什么,我又不想用状态」。
> 状态:**建议,未拍板**。

"不想用状态"恰好与最标准的做法同向。三段式**不需要**一个 phase 枚举状态机:

### 7.1 存时刻,不存阶段(**已修正:光有两个时刻不够**)

权威 DS 持有**两个绝对时刻**(单调钟,`FPlatformTime::Seconds()`,理由同
`BattleTimeLimitDeadlineSeconds` 的注释:跨整局的窗口足够长到让 Pod 的 NTP 步进落进来):

```
PrepareDeadline = 准备阶段结束时刻
SettleDeadline  = 结算阶段结束时刻(终局裁决那一刻才算得出来)
```

> **本节初稿的洞(2026-08-12 自查修正)**:初稿写的是 `PrepareDeadline` + `BattleDeadline`
> 两个时刻就能派生全部三段。**这是错的**——「战斗 → 结算」的边界**不是时间驱动的**:
> 一局可以在时限到达之前就因终局裁决(全灭 / 有人撤离 / 目标达成)提前结束。
> 纯时间派生只能表达"打满了",表达不了"提前结束了"。

**但这不需要新加状态**——"终局已裁决"这个事实**代码里已经存着了**:
`TerminalDeliveryState`(`HasPendingResult` / `IsReceiptAcknowledged` / `IsTerminalAcknowledged`),
现有代码已经在拿它当闸门用(`TickBattleTimeLimit` 开头的终态门、`HandleMonsterEntityDied`
的"终局阶段不再产生新掉落")。于是:

```
Phase(Now) =
    Now < PrepareDeadline                     -> 准备
    !TerminalDeliveryState.HasAnyTerminal()   -> 战斗   // 含"打到时限"这一路:到点即裁决
    Now < SettleDeadline                      -> 结算
    otherwise                                 -> 退出场景
```

四个输入里,`TerminalDeliveryState` 是既有的,只新增两个 `double` 时刻。
**依然没有 phase 变量,没有 `SetPhase()`,没有转移表**——阶段仍是纯函数,
不存在"阶段"与"倒计时 / 终局事实"两份事实漂移(§9.22)。

### 7.1.1 唯一收口:阶段必须有**一个**只读访问器

"不用状态"最容易退化成的形态是:**每个消费者各写一遍时间比较**——
GameMode 一处、掉落一处、输入门控一处、HUD 一处。那比状态机更糟(判据散落 N 份,
改一次判据要找齐 N 处,漏一处就是隐蔽 bug)。

所以派生必须收口成**一个**权威只读访问器(如 `APandoraBattleGameMode::GetPhase()`),
所有消费者只准问它,**不准自己比较时刻**。这条与 §9.22 是同一条:唯一权威 + 派生按需计算,
但"派生逻辑本身"也只能有一份。

### 7.1.2 一次性副作用用幂等 latch,不用状态机

"准备阶段结束时要 arm 战斗时限"这类**只能发生一次**的副作用,不需要为它引入状态机——
仓库里已有现成写法:`bBattleTimeLimitArmed`(幂等,两处调用谁后到谁生效,条件不满足直接 return)。
新增副作用照抄这个模式即可。

### 7.1.3 什么时候我会改口说"该上状态机"

以下任一成立时,线性时间轴不再成立,那时状态机才是对的工具(**现在都不成立**):

- 阶段出现**分支或可跳过**(ban-pick 可选、准备阶段可提前开始又可回退);
- 阶段需要**暂停 / 重开**(掉线宽限、GM 暂停);
- 战斗阶段内部**再分段**(wave1 → wave2 → boss,每段有自己的目标与时限);
- 阶段可以**回退**(结算界面退回战斗)。

判据很简单:**只要阶段仍是"单向、线性、要么到时间要么出事实"**,派生就够,
加状态只是多一份会漂移的事实。

### 7.1.4 对照:LoL 那种游戏要不要状态机?(2026-08-12 用户问)

**要,但不在 DS 里。** 拆开看这类 MOBA 的完整链路:

| 段 | 在哪 | 形态 | 该不该状态机 |
|---|---|---|---|
| **选人 / ban-pick** | **对局服务器之外**(独立的选人流程,玩家还没进游戏) | 有分支、有每步超时、有玩家交互、有人跑了要回滚整局 | **该**——这是真正的多步流程 |
| **载入 → 出门期** | 对局服务器内 | 单向、线性、时间驱动 | 不该,派生即可(= 我们的准备阶段) |
| **对局** | 对局服务器内 | 单向,到时间或出事实才结束 | 不该 |
| **结算 → 退出** | 对局服务器内 | 单向、时间驱动 | 不该 |

**关键结论:玩家踏进 DS 那一刻,阵容已经定死了,DS 内部剩下的就是线性三段。**
需要状态机的那一段(选人)在**进场之前**就已经跑完并且**不占用 DS**——
不会为了等 10 个人选 60 秒英雄而占着一台已分配的 GameServer。

**对我们的直接推论**:将来真要做 ban / pick,**不要塞进准备阶段**。
理由不只是"会把线性时间轴污染成状态机",还有更硬的一条:ban-pick 期间玩家**还不该在 DS 里**。
本仓库其实早就这么归口了——`pvp-rules.md` §5 的待决策清单里,
`Ban / Pick` 一行的"影响代码"写的是 **matchmaker**,不是 battle DS。
它和现有的"撮合确认(confirm)"是同一层,与 §1.1① / §3.2⑧ 两条完全一致。

**暂停(pause)是唯一真正落在对局内的例外,但它也不该做成状态**:
暂停的本质是**时间轴被冻结**,不是"多了一个 Paused 阶段"。派生方案里它反而最自然——
把两个 deadline 按暂停时长**整体平移**(或暂停期间不推进单调钟基准)即可,
阶段函数一行都不用改。做成状态机反倒要在每个转移上补"如果暂停中"的分支。

### 7.2 下发也不发状态,发剩余秒数

客户端要显示"准备中 剩余 N 秒",**发 N 就够了**,不必发阶段枚举——
现成先例就是 `AMyGameState::BattleRemainingSeconds`(权威端整秒推,客户端纯投影)。
UI 上"现在是哪一段"由秒数派生。**代价**:仍是新增复制属性 → `PandoraNetProtocolVersion` 9→10。

> 若想连协议版本都不 bump:复用 `BattleRemainingSeconds` 一条通道,用**约定编码**区分两段
> (如负值 = 准备阶段剩余秒)。**不推荐**——那是把两个语义塞进一个字段,省一次版本 bump
> 换一个长期歧义,违反 §15 的"直达"。**版本 bump 是正常成本,不值得为它扭曲协议。**

### 7.3 结束条件也别做成状态机

准备阶段结束 = `全员就绪(§3.2 判据) 或 Now >= PrepareDeadline`,**每 tick 求值一次即可**——
与现有 `TickBattleTimeLimit` 同款(它已经是"每秒重算 + 到期动作幂等"的写法,
刻意不停表、靠下一拍重试)。不需要 `Preparing → Fighting` 的转移表。

**唯一真正需要存的**,是那些**不可重建的事实**(谁死了 / 谁撤离了 / 终局快照冻结没有)——
这些现在已经用集合与 `TerminalDeliveryState` 存着了,不属于"阶段状态"。

### 7.4 PVE 的"提前结算"用同一把尺子解决

同理,**别给"怪物清空"新造一个终局触发**(那会在 §2.1 那个"唯一权威入口"的枚举旁边
再开一个裁决源,注释已明令禁止)。标准做法两条:

1. **胜负判据留在策略对象里**(`UPandoraBattleSettlementRule` 子类)。类头注释已经预留了
   "击杀 Boss / 存活 / 护送"是不同规则子类——新玩法 = 新规则子类或换实例,不改 GameMode,
   也不加触发枚举。
2. **把"目标达成"和"对局结束"拆开**:目标达成(怪清空 / Boss 死 / 护送到点)**不直接收局**,
   而是**结束战斗阶段、进入结算阶段**;玩家在结算窗口里捡东西、看战报、走撤离,窗口到点才退场景。
   §2.1 记的那个"提前结算"感受,根因就是这两件事现在是同一件事——三段式本身就是解药,
   不需要额外的状态。
